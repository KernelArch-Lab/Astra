\section{Design}
\label{sec:design}

Three primitives carry the design: the \captoken, the
\texttt{CapabilityManager} that mints and revokes tokens, and the
\capgate that fronts every IPC operation.

\subsection{Token format}
\label{sec:design:token}

A \captoken is a fixed-size value type (\Cref{fig:token}): passed by
value, copied freely, no pointers inside. The authoritative state
lives in the \texttt{CapabilityManager}'s pool; the token itself is
keying material that names a slot.

\hline

\texttt{m\_arrUId[0]} : random       & 32 \\
\texttt{m\_arrUId[1]} : random       & 64 \\
\texttt{m\_ePermissions}             & 64 \\
\texttt{m\_uEpoch}                   & 64 \\
\texttt{m\_uOwnerId}                 & 64 \\
\texttt{m\_arrUParentId}             & 128 \\
\hline
\end{tabular}
\caption{Token wire layout. The high half of \texttt{m\_arrUId[0]}

\label{fig:token}
\end{figure}

The 128-bit identifier splits as 32 bits of slot index plus 96 bits
of randomness. That split is the central design choice of the paper,
and \Cref{sec:design:fastpath} spends some time justifying it.

\subsection{Permission monotonicity}
\label{sec:design:mono}

A child derived from a parent token may carry only a subset of the
parent's permissions. \texttt{CapabilityManager::derive} enforces
this; asking for a non-subset mask returns \texttt{Result::error}.
The CBMC bounded-model proof (\Cref{sec:impl:cbmc}) checks the
invariant across all parent/child permission pairs in the supported
bitmask.

This is the standard capability discipline: once a permission has
been dropped somewhere along a derivation chain, nothing below that
point can get it back---you have to return to a more privileged
ancestor. \sysname deliberately has no \textit{regrant} operation.

\subsection{The slot-indexed validate fast path}
\label{sec:design:fastpath}

The most consequential decision in the system is the shape of
\texttt{validate}.

\para{Why the natural design is too slow}
A conventional validate looks like this: hash the 128-bit identifier
into a side table, load the bucket, walk a chain, and on a match
check epoch, permissions, and revocation state. Even with a perfect
hash that is a load for the bucket head plus a compare; with
collision chains it can be two or three cache misses before the
compare even starts. The producer and the consumer each validate once
per message, so on a sub-microsecond fastpath this one function
dominates everything else we do.

\para{Our approach}
Embed the slot index in the identifier itself:

\begin{equation*}
\texttt{m\_arrUId[0]} \;=\; (\text{slot}_{32} \ll 32) \;|\;
                            \text{rand}_{32}
\end{equation*}

\noindent
\texttt{validate} then runs:

\begin{verbatim}
if (!token.isValid())    return false;
// epoch sanity: reject tokens claiming
// an epoch that hasn't happened yet
if (token.epoch > current_epoch)
    return false;
if ((token.perms & required) != required)
    return false;
slot = token.uid[0] >> 32;
if (slot >= max_tokens)  return false;
TokenSlot& s = pool[slot];  // 1 load
if (!s.active.load(acquire))    return false;
if (s.revoked_at.load(acquire)) return false;
return asm_ct_compare(s.token.uid,
                      token.uid, 16) == 0;
\end{verbatim}

\noindent
Everything before the pool access runs in registers---epoch sanity,
permission subset, slot bounds---and the constant-time compare over
the full 128 bits has the last word. The listing mirrors the shipped
\texttt{CapabilityManager::validate} check-for-check, in order.

\para{Why this is safe}
The slot index is a hint, never a credential. Forging one buys an
attacker a deterministic indirection into the pool and nothing else,
because the full-width compare still has to match; the forgery space
stays at $2^{96}$. The bounds check means an out-of-range index
rejects without ever touching memory out of bounds
(\Cref{sec:eval:correctness}, T-OOB).

\para{Why this is fast}
The data-dependent work is one shift, one load of
\texttt{pool[slot]}, and one 16-byte \texttt{ct\_compare}. The slot
load is the only memory access on the path.
\Cref{fig:figure-2} shows the cost staying flat from 16 to 4090
active tokens.

\para{Constant-time compare}
The identifier match uses the M-21 \texttt{asm\_ct\_compare}
primitive, which folds all sixteen bytes through a running OR before
producing its one-bit verdict. A short-circuiting compare here would
leak which byte differed first and open a chosen-token search over
already-allocated slots; constant time is not optional.

\subsection{Cascading revocation}
\label{sec:design:revoke}

\texttt{revoke(t)} finds $t$'s slot in $O(1)$ by the same slot-index
trick, stamps the slot's \texttt{m\_uRevokedAtEpoch}, publishes
deactivation with a release store, and securely wipes the token bytes
(\texttt{asm\_secure\_wipe}). Any \texttt{validate()} that starts
after the release store rejects on the slot flags. One that raced
ahead and saw \texttt{active==true} still rejects, because its
constant-time compare now runs against wiped bytes. Each revoke
transaction also bumps a global epoch counter, which does two jobs:
validate uses it to reject tokens claiming an epoch that has not
happened yet, and every token revoked in one cascade carries the same
stamp, which keeps audit records coherent per transaction.

The cascade then takes down all live descendants of $t$. Tokens carry
a parent \emph{backpointer} (\texttt{m\_arrUParentId}) but no forward
child list---a deliberate choice that keeps them fixed-size value
types with no heap state---so children are found by sweeping the
bounded pool once per BFS layer, $O(N)$ per visited node with
$N \le 4096$. We state this plainly rather than calling it $O(d)$:
the cascade is bookkeeping under the manager's spinlock, off the
message fastpath. What the security argument needs---and what
\Cref{sec:eval:revoke} measures---is \emph{time-to-effect}, the
interval from the \texttt{revoke()} call to the first rejected
message, and that is independent of pool occupancy because rejection
rides the $O(1)$ slot-flag check inside validate.

A revoked slot is recycled on a later \texttt{create()}. The wipe has
already destroyed the 96 random bits, so a stale token can never
match a recycled slot.

\subsection{The capability gate on the IPC fastpath}
\label{sec:design:gate}

The \capgate binds a \texttt{CapabilityManager*} and a
\texttt{CapabilityToken} to one endpoint of a channel
(\Cref{fig:gate}). A typical channel carries two gates: the
producer's, stamped \IPCSEND, and the consumer's, stamped \IPCRECV.
\texttt{writeGated()} validates \textit{before} claiming ring space;
\texttt{readGated()} validates before consuming.

\begin{figure}[t]
\centering
\includegraphics[width=0.95\columnwidth]{figures/gate_path}
\caption{The gate on the IPC fastpath. \texttt{CapabilityGate} sits
in front of the existing \texttt{RingBuffer::write/read} machinery;
a failed validate mutates no ring state.}
\label{fig:gate}
\end{figure}

\para{The denied-request invariant}
A denied request must leave \texttt{m\_uWriteClaimIndex} and
\texttt{m\_uWriteIndex} untouched. Give this up and a revoked
principal can deny service to a whole channel by burning claim space
it never commits. T-RingFP (\Cref{sec:eval:correctness}) exercises
the invariant directly, asserting that neither index moves under any
of the three deny modes: unbound gate, missing permission, revoked
token.

\para{The blocking-read invariant}
\texttt{readWaitGated()} re-validates after every futex wake-up. A
token can be revoked while its reader sleeps; deliver a message on a
stale wake and the gate has a window. Re-validating closes it, at
the price of one extra \texttt{validate()} per wake---well under
100\,ns.
